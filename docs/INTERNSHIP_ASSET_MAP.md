# 漫序：实习方法与公开资产映射

整理日期：2026-10-03。用途：为漫序的个人工作台迭代提供可追溯的内容与验收依据。

本文梳理公开仓库和用户主动提供的履历截图，不读取企业内部材料、模型密钥或私人生成数据库。本文所列 Skill 是开源方法与工具资产，不表示它们已安装为当前会话技能，也不表示漫序已经实现自动调用。

## 1. 定位与时间线

**建议定位：漫序是将快看漫画实习期间形成的研究、评测、人工确认、局部返工和质量检查方法，继续实现为个人 AIGC 产品与创作工作台。** 创作流程与方法证据应相互连接，而不是仅增加更多生成按钮。

| 时间与材料 | 能说明什么 | 不能据此说明什么 |
|---|---|---|

| 2026-09-22，漫序课程 MVP v1.0.0 与 PRD v1.1 | 原仓库已明确作为本地单用户课程作品，已有分镜编辑、真实 Pi 剧本样例、原创静态示例素材、配音字幕与 MP4 合成 | 不回写为 2026 年 3–5 月已经在快看上线的官方产品 |

| 本次迭代 | 在保留课程原始记录的基础上，向个人实习方法沉淀工作台扩展 | 不冒用快看品牌、内部业务资料或企业官方产品身份 |

## 3. 六项公开 Skill 的准确映射

本次在 2026-10-03 通过 GitHub 仓库页面或公开 API 核实：以下六个仓库存在、为公开仓库、默认分支为 `main`。`research-to-prototype`、`tob-demand-scoping` 等可作为扩展资产，但不是履历截图对应的这六项。

### 3.1 模型评测全流程

- 仓库：[model-eval-workflow](https://github.com/Yiheng-guo/model-eval-workflow)。
- 输入：评测目标、冻结的任务与 case 集合、候选模型/系统版本、Prompt 与采样配置、评审规则、逐条结果、重试记录和费用凭证。
- 输出：目标卡、维度和一票否决、评测集、评分标准、试标对齐记录、批量结果、Bad Case、报告。`scripts/audit_results.py` 可对录制结果做离线审计。
- 可核实的例子：[合成离线审计](https://github.com/Yiheng-guo/model-eval-workflow/blob/main/examples/offline/CASE.md)。A 含待裁定项不能入选；B 触发硬否决，不能被平均分挽救；缺少 T2 的反例被拒绝。这是合成记录审计，没有真实模型调用或当前模型排名。
- 工具验收：冻结 `case_ids` 不得为空或重复；每个候选的结果集合必须完整且无多余项；`pass/fail/pending` 分别统计；待裁定和硬否决独立保留；未知费用不填为零。
- 边界：脚本校验记录的一致性，不判断自然语言质量、不替代独立评审。远端 2026-10-02 增强版已指出，30/100 条和 80% 是场景示例，不是所有任务通用的统计充分性或校准门槛。单条输入只适合烟雾测试，不能外推总体排名。
- 工作台适配：目标卡 → 冻结用例 → 规则版本 → 原始结果/盲评 → 不通过项证据 → 复验与决策。展示实际样本量、评审来源和计费状态；不要把手填标签做成自动模型评分。

### 3.2 AI 产品证据拆解

- 仓库：[ai-product-teardown](https://github.com/Yiheng-guo/ai-product-teardown)，基于上游 MIT 项目二次开发，原作者与来源记录见仓库。
- 输入：真实产品界面、截图、操作顺序、可观察状态、官方资料与明确任务范围。
- 输出：证据台账、用户旅程、可观察 Agent 契约、功能等价设计、产品判断、同任务比较和验证计划；区分已确认、合理推断、建议设计、未知。
- 可核实的例子：[虚构产品“稿舟”](https://github.com/Yiheng-guo/ai-product-teardown/blob/main/examples/product-decision-demo.md)。聊天称完成、任务仍运行、资产为空，只能确认当时状态不一致；不能据此确认后台失败、重复扣费或用户体验指标。
- 工具与验收：该仓库包含公开审计索引查询器和测试，不是“一键自动拆解现实产品”的执行服务。重要结论引用证据 ID；同时核对聊天、任务、资产与实际预览；建议实验不能写成已执行结果。
- 边界：虚构例子不是 OiiOii 实测；官方宣称不等于可观察行为；不声称读取私有 Prompt 或隐藏架构。
- 工作台适配：产品研究卡 → 证据条目 → 体验问题 → 需求候选 → 尚未执行的验证计划。保留来源、日期、版本和证据类别。

### 3.3 剧本策划与约束检查

- 仓库：[aigc-script-development](https://github.com/Yiheng-guo/aigc-script-development)。
- 输入：创意、受众、目标集数/时长、人物设定、固定开结尾、不可更改约束，以及已写出的场景与人工约束判断。
- 输出：完整剧本、人物动机、约束编号与证据、未完成部分、人工确认事项；`scripts/run.py` 检查标注、集数和时长。
- 可核实的例子：[失物归还合成案例](https://github.com/Yiheng-guo/aigc-script-development/blob/main/examples/CASE.md)。正例是一集八秒的场景：林不解锁手机，交给管理员。反例要求两集却只有一集，且场景正文写偷看聊天记录；已有人工 `fail` 标注与位置证据，工具输出 `blocked` 并退出 2。
- 验收：每条硬约束记录 `pass/fail/unknown` 和文本位置；缺集数、失败或未知检查不能进入确认后的制作阶段。正文必须实际存在，大纲不能冒充完整剧本。
- 边界：工具消费给定的约束判断，不自动理解人物动机；自己填入的 `pass` 不是独立内容评审。合成样例不是实习剧本。
- 工作台适配：在现有故事输入和分镜前增加“目标与硬约束”“剧本版本”“确认意见”。第一次生成保留草稿状态，后续制作引用明确的已确认版本。

### 3.4 分镜与连续性规划

- 仓库：[aigc-storyboard-planning](https://github.com/Yiheng-guo/aigc-storyboard-planning)。
- 输入：已确认剧本、角色/场景/道具参考、画幅风格时长、镜头与起止状态。
- 输出：镜头卡、角色/场景/道具状态表、准确台词及说话人、生成要求、人工视觉检查。`scripts/run.py` 对相邻同场镜头比较稳定状态键。
- 可核实的例子：[一部手机的连续性](https://github.com/Yiheng-guo/aigc-storyboard-planning/blob/main/examples/CASE.md)。SH01 结束 `phone.owner=lin, phone.count=1`；SH02 正例保持一部并交给管理员。反例开始变为两部且无解释，输出具体差异 `phone.count:1→2`，状态 `blocked`、退出 2。
- 验收：同场上一镜终态与下一镜初态一致，或有明确转场/换装/变化原因。参考资产、镜号、场景、准确对白、时长都可追溯。
- 边界：状态表一致不证明实际图片脸、手、道具数量或口型正确；无生成媒体只能称规划完成，不能声称已锁脸。没有固定九宫格或强制所有项目 16:9。
- 工作台适配：现有分镜旁增加连续性状态与确认信息，预演时连接前后镜。角色 ID 应稳定，文字档案和实际参考图检查分别显示。

### 3.5 媒体问题定位与局部修复

- 仓库：[aigc-media-badcase-review](https://github.com/Yiheng-guo/aigc-media-badcase-review)。
- 输入：有使用权的成片、源文件映射、采用区间、问题时间、预期表现、音轨策略与复验记录。
- 输出：问题表、成片到源区间映射、原因假设、最小修复动作、局部/相邻镜/整集复验。
- 可核实的例子：在合成八秒片中，成片 4.5–5.5 秒映射到 SH02 的源片 2.5–3.5 秒。失败例即使局部与邻镜 `pass`，整集 `pending` 仍 `blocked`。后来实际合成 `before.mp4/after.mp4`，禁用 SH02 的 660 Hz 测试音，保留 880 Hz 画外测试音；`repair-measurements.json` 记录 5.0–5.4 秒 PCM 频谱隔离结果。
- 验收：`local/adjacent/full_episode` 三项全部通过才能接受修复；每项有证据文件。生成错误与混音错误应通过隔离对照区分，根因未验证时保留假设。
- 边界：时间映射工具仅适用于 1 倍速硬切，变速和叠化需要显式时间映射；脚本本身不修图或重新生成。测试音 A/B 证明混音层隔离，不证明自然对白听感、口型、视觉生成或真人审片质量。样例中的 `CASE.md` 与输入测量证据应一起读，不能只看到 `review_complete` 就宣称业务质量通过。
- 工作台适配：成片页创建问题区间，关联镜头/源素材/版本，记录修复建议与三个复验状态。仅局部改善时继续保留待验收，不自动显示已修复。

### 3.6 剪辑与视频交付检查

- 仓库：[aigc-video-delivery](https://github.com/Yiheng-guo/aigc-video-delivery)。
- 输入：确认素材及许可、JSON 剪辑清单、采用区间、原声/画外音/字幕、画幅和费用凭证。
- 输出：MP4、SRT/ASS、技术检查报告、人工审片状态、按币种及凭证状态分类的费用台账和文件 SHA256。
- 可核实的例子：[实际合成渲染](https://github.com/Yiheng-guo/aigc-video-delivery/blob/main/examples/CASE.md)。FFmpeg 测试图案与正弦测试音经过真实区间剪辑，生成八秒 720×1280、24 fps 测试片并检查完整解码。失败清单计划八秒但素材区间合计十一秒，退出 2；技术报告保留人工审片 `pending`、生产 API 成本 `unknown`。
- 工具验收：`render.py --schema-only` 仅检查结构，`--validate-only` 再检查真实源文件/时长/音轨，实际渲染后独立解码；拒绝默认覆盖旧产物。`delivery_audit.py` 审计字幕时间和费用账目。
- 边界：这个独立渲染器当前仅支持 720×1280/24 fps；不要与漫序原渲染器的横屏/竖屏能力混写。合成测试片不是 AI 短剧；完整解码不等于人工内容审片。没有凭证不把 Token、赠送额度、充值或未知 API 花费混为真实现金支出。
- 工作台适配：制作版冻结 → 素材检查 → 技术合成 → 播放审片 → 明确交付结论。技术完成与内容验收分别展示，不由 worker 的成功状态替代审片结论。

## 5. 适合工作台的最终信息结构

### 工作台入口

主入口应同时回答“我下一步做什么”和“这套方法有什么依据”。建议保留作品制作入口，并增加研究、评测、方法与复盘的联系：

1. **工作总览**：近期作品、待确认剧本/分镜、待修复问题、待审片交付；不存在的统计不填造数据。
2. **作品制作**：继续复用故事、角色、分镜、画面、配音成片；明确草稿与已确认版本。
3. **质量复核**：镜头连续性、成片问题、修复动作、三层复验；未做检查显示待检查。
4. **研究与评测**：研究证据和评测记录。以保存的实际记录为事实来源，输入、规则与原始输出一起留存。
5. **方法资产**：六项 Skill 的问题、输入、产物、验收、正反例、能力限制、源码与上游来源。点击“查看方法/案例”与“执行工具”必须有语义区别。
6. **实践复盘**：分别展示用户自述经历、课程 MVP、后续个人开源和本轮实际验证；不以卡片数量制造成效。

### 每条研究、评测或问题记录的共通字段

`记录 ID / 项目与版本 / 记录类型 / 来源与日期 / 原始输入或位置 / 可观察表现 / 验收规则及版本 / 判断 pass-fail-pending-unknown / 判断者及方式 / 证据引用 / 下一步与复验 / 费用凭证状态`。

所有方法卡需要显式显示它当前是“可参考的方法资产”“可在命令行运行的工具”，还是“已在漫序集成并验证的能力”。仓库有工具不等于网站已经接入它。

### 四个建议验收门

- **剧本门**：内容与硬约束检查后记录人工确认的具体版本；未确认可探索但不得当制作定稿。
- **分镜门**：连续性状态与实际画面各自审核；规则匹配不能替代视觉审查。
- **修复门**：局部、相邻镜与整集都有结果；pending 不算通过。
- **交付门**：技术产物存在、能播放下载，与内容审片分别记录；缺审片或凭证保留未知。
